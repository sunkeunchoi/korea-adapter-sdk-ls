# Concepts

Shared domain vocabulary for this project — entities, named processes, and status concepts with project-specific meaning. Seeded with core domain vocabulary, then accretes as ce-compound and ce-compound-refresh process learnings; direct edits are fine. Glossary only, not a spec or catch-all.

## TR & dispatch

### TR
One LS-securities API operation, identified by a transaction code (e.g. `t1102`, `CSPAQ12200`). The SDK models each TR as a request/response pair plus a runtime endpoint policy, and tracks per-TR metadata (facets, support tier, provisional facets) independently of every other TR. The unit this whole codebase is organized around.
*Avoid:* transaction (generic), endpoint (a TR is more than its path — several TRs can share one path, distinguished by the transaction code).

### owner_class
The dispatch class a TR is routed through, naming which SDK handle exposes it and which runtime machinery it uses: market-session reads, single-page paginated reads, account-state reads, realtime/websocket, order operations, plus a placeholder used before a TR's class is confirmed. A TR's owner_class is corrected from the placeholder to its real class only when the TR becomes callable.

### Facet
A single classified property of a TR (its session scope, instrument domain, rate bucket, pagination behavior, caller-supplied identifiers, and similar). A facet is either hard-accurate (confirmed against the captured spec) or provisional (best-effort, pending live confirmation — tracked in the Provisionality Ledger).

### In-block / Out-block
The named blocks of a TR's wire payload: an in-block carries the caller-supplied request fields, an out-block carries one section of the response. A single TR may expose several out-blocks — commonly a single-record header block alongside a repeated-row array block — and each block's name is the load-bearing key the SDK struct binds to.

### Normalized baseline
The projected, committed record of a TR's wire shape — field names, types, and block structure — derived mechanically from the raw OpenAPI capture, never hand-authored. It is what drift detection observes and what struct authoring starts from.

It is a snapshot, not a runtime oracle: it can under-report a request block (omit fields the gateway accepts or requires). Once a TR's request struct has been certified against the live gateway, that certified shape is the stronger witness and wins any disagreement with the baseline — the baseline alone is the floor for an unimplemented TR, not the ceiling for an implemented one.

### Body-cursor continuation
How LS chart TRs actually paginate on the live gateway: the response out-block echoes a body cursor (continuation date/time fields), and the next page request must thread that cursor back **and** set the `tr_cont: Y` transport header — either alone re-serves the newest page. The `tr_cont`/`tr_cont_key` transport headers terminate after the first page even while in-range rows remain, so a header-driven walk silently truncates a multi-page range to its newest page. Every page dispatch must individually pass the TR's own per-TR rate cap (the runtime limiter enforces only the category bucket).

### Degenerate chart window
A chart-TR date-window request the LS gateway declines to filter: when the requested window collapses — a single-day window (`sdate == edate`) or a single-row request — the gateway ignores the start date and serves its default lookback, up to the requested row count ending at the end date, instead of the window. A wide multi-day window is filtered correctly, so the only probe shape that proves the filter is live is a wide window varying one boundary against a known-closed control day. Consequence: a caller that issues a single-session request and trusts the response to be that window operates on a false premise — a catch-up expecting one new session's bars can receive years of history, and appending that response untrimmed collides with stored coverage. Observed on the daily chart TR (t8410) in both flavors; kin to [[Body-cursor continuation]] as live-gateway wire behavior that contradicts the documented request contract.

### Rolling call budget
The second, unpublished layer of LS gateway throttling behind `IGW00201`. The official docs publish only per-TR per-second caps (`transactionPerSec` / `requestLimit`), but the same error code also fires from a cumulative call-count budget that a correctly per-second-paced bulk pull still exhausts once the window is warm — the two layers are distinguishable only by whether steady pacing avoids the error. The budget is shared across everything dispatched on the credential; its size, window, and exact bucket scope are not published anywhere and must be measured empirically. Consequence: a deep multi-symbol bar pull is budget-bound, not rate-bound — no per-second pacing makes it fit, only spend planning against the budget does. Live evidence later added a third, short-window dimension: the budget punishes dispatch *density* (back-to-back continuation-page bursts trip it while the same reads paced seconds apart always serve) and weighs response *bytes* (one ~800KB master read drains the window for the reads dispatched behind it), and this short window refills in roughly two minutes — so burst shape, fetch ordering, and page-level (not walk-level) backoff-retry matter alongside total spend.

## Support lifecycle

A TR climbs a three-rung support ladder; each rung is a deliberate, separately-gated promotion.

### Raw
Below Tracked: the TR's wire shape exists in the captured OpenAPI universe (raw capture, `code-set.json`, migration-source dependency map) but it has no committed `metadata/trs/<tr>.yaml` and no normalized baseline, so it is not yet observed for drift and the `implement-tr` recipe cannot derive structs for it. Bringing a raw TR to Tracked — authoring metadata and pinning a baseline from the raw capture — is a prerequisite step that earlier waves did not face because their members were already Tracked.

### Tracked
The lowest *maintained* rung: the TR has committed metadata and a maintained baseline but no callable code. It is observed for drift, nothing more.

### Implemented
The middle rung: the TR has hand-authored callable Rust and has passed a Paper Live Smoke (a representative call that constructs, returns a success code, yields a non-empty result, and deserializes). An Implemented TR is callable but carries no recommendation and no recorded evidence — explicitly *not* endorsed for production use.

### Recommended
The top rung: an Implemented TR additionally cleared for production use, backed by recorded Focused Evidence and a recommendation block. Promotion to Recommended is a separate, deliberate act beyond Implemented. As of the [[Error-resilience gate]] it additionally means "this call fails gracefully" — promotion requires passing the gate (error coverage), not just a green happy-path smoke.

### Error-resilience gate
The blocking condition, layered on top of the happy-path [[Paper Live Smoke]] + [[Focused Evidence]] + recommendation block, that a TR must pass to reach [[Recommended]]. It redefines the badge to mean "this call fails gracefully": invalid input is caught before the network call ([[Preflight validation]]) and every reachable gateway error is explained. Its per-TR evidence is [[Error coverage]], produced by the [[Differential negative probe]].

### Preflight validation
Rejecting an invalid request *before any network call* with a typed `LsError::Invalid { field, reason }`, from a per-TR [[Constraint schema]]. Runs at the single `dispatch_once` seam (so it covers every owner_class, including orders). Deliberately **permissive by default**: only `type`/`required` (grounded against the normalized baseline) always block; value-class bounds (enum/range/format) stay permissive until a live probe confirms them, because a false-reject silently breaks a caller's valid request with no detector.

### Constraint schema
A declarative per-TR sidecar (`metadata/constraints/<tr>.yaml`) describing each request field's type, required-ness, and per-input-class markers (enum/range/format, each explicitly N/A when inapplicable). The single source from which preflight validation, the negative probe, and the Reference "Errors & validation" section are all derived. Grounded offline against the TR's normalized baseline — but required-ness must also agree with **every** in-repo caller of the TR's request struct, not just the certified smoke chain (the struct wins on disagreement, permissive direction): a second caller may legitimately send empty a field the smoke chain fills, and an over-strict `required: true` surfaces only as a runtime false-reject, never at authoring time.

### Differential negative probe
The operator-run probe that certifies a [[Constraint schema]] against paper: a valid control request plus each mechanically-generated invalid variant run in the *same session*, so the injected violation — not an environment condition — is what a rejection reflects. Outcomes per variant: CLEAN (control ok, variant [[Merits reject|rejected on merits]]), DIVERGENT (control ok, variant accepted — blocks promotion), or HELD (inconclusive). HELD has two distinct causes: the control itself failed, or the variant met a [[Non-evaluation]] the gateway never judged (a throttle) — either way the injected violation is not what the response reflects, so it is re-probed, never read as a confirmation. Gates re-promotion, never the offline CI gate.

### Merits reject
A variant response the gateway produced by **evaluating the injected violation on its merits and refusing it** — the signal a CLEAN outcome depends on. It is defined by the *rejection reason*, not the HTTP status (an ingress-validation reject arrives with a 5xx status) and not by "any non-success code": a reject is on-merits only if it is a recognized merits-reject code, which spans two layers — gateway-**ingress** codes and exchange-**business** codes (a blank required field refused by the exchange is a business-layer merits reject, not an ingress one). Anything the gateway did *not* judge on merits is a [[Non-evaluation]], not a merits reject. The set of merits-reject codes is a per-leg allowlist seeded from that leg's certified [[Error coverage]] evidence, never inferred from the gateway-ingress code family alone.

### Non-evaluation
A gateway response that carries **no signal about the injected constraint** because the gateway never judged the variant on its merits — canonically the `IGW00201` throttle (the request was refused for pacing/budget — see [[Rolling call budget]] — before evaluation), plus transport failures and unknown codes. A [[Differential negative probe]] variant that meets a non-evaluation is inconclusive → HELD, never CLEAN; treating a non-evaluation as a rejection is the false-CLEAN a strict merits-allowlist classifier exists to prevent.

### Booking-determining field
A submit-leg request field whose omission changes **what order gets booked** rather than whether the request is rejected — canonically `CSPAT00601 BnsTpCode`, where the gateway defaults the buy/sell direction and places a real order (ledger §30, `ordno=17093`). Such a field stays `required: true` as a hard caller contract and is **never fired live** by the [[Differential negative probe]]: the exclusion is code-enforced — its [[Constraint schema]] marks the exact pair `booking_determining: [required]`, and the probe's fire loop consumes the annotation (`order_variant_may_fire`) to record-not-dispatch the variant, so it is structurally unroutable rather than an operator convention. A never-observed submit field with booking-shaped semantics is annotated provisionally (fail-closed); only a harness-confirmed rejection lifts it, never semantic judgment or schema relaxation. See `docs/solutions/conventions/order-negative-probe-modify-vs-submit-policy.md`.

### Error coverage
The per-TR evidence artifact (`metadata/error-coverage/<tr>.yaml`) recording the [[Differential negative probe]]'s per-(field, class) outcomes plus the reachable gateway codes the Reference page explains from the shared error catalog. Required on a Recommended TR by the validator ([[Error-resilience gate]]).

### Paper Live Smoke
A credential-gated integration test that hits the real LS *paper* gateway with real credentials to prove a TR is genuinely callable. It is the gate for flipping a TR to Implemented; a smoke that returns an empty result leaves the TR callable-but-unconfirmed (pending), not Implemented. For `realtime`/websocket TRs the gate is instead *lifecycle (Transport) reachability* — a clean connect → subscribe → unsubscribe — and a row that does or does not arrive is bonus, not the gate; row contents stay provisional until a separate FrameDecode pass.

### Finish-the-flip
A Tracked TR whose callable Rust is **already fully wired** — request/response carrier, `{TR}_POLICY` registered in both crosscheck lists, a `live_smoke_{tr}` and Makefile target — yet still sits at `support.implemented: false` because its certifying [[Paper Live Smoke]] has not yet returned a non-empty in-window result (typically a prior wave staged the build under a closed window or an empty paper feed). For a finish-the-flip TR the remaining work is **metadata + docgen only**, never authoring: re-run the existing smoke, and on a non-empty witness flip `implemented` and bump the docgen counts. Re-authoring one collides on its already-defined symbols, so a flip wave greps for an existing carrier/smoke before treating a candidate as needing an `implement-tr` pass.

### Connection-reachable-only
The calibrated reachability claim a `realtime`/websocket TR carries when its lifecycle smoke passes but the subscribe path is fire-and-forget (the SDK never reads the subscribe ACK) and the gateway emits no observable rejection for an invalid `tr_cd`. A clean connect → subscribe → unsubscribe then proves the *connection* works, not that the specific channel is individually reachable — so the TR is Implemented but its claim is recorded as connection-reachable-only, not per-TR-reachable. Earning the stronger per-TR claim requires the SDK to read the subscribe ACK (a separate capability). Established empirically by the WebSocket negative control.

### WebSocket negative control
The check that calibrates a realtime reachability claim: subscribe a deliberately-invalid `tr_cd` and observe whether the gateway signals a rejection. A `tr_cd`-attributable inbound body (non-empty `rsp_cd`) is `OBSERVABLE` (per-TR reachability is provable); a bare stream close or decode error is `INCONCLUSIVE`; pure silence is `NOT-OBSERVABLE` (flips are [[Connection-reachable-only]]). It has a deterministic mock-WS twin and a live half (`make live-smoke-ws-negative`); its verdict gates how strong a flip's claim may be, not whether the flip happens.

### Closed-window reachable
A curated per-TR judgment that a read's [[Paper Live Smoke]] can certify a non-empty result while KRX is closed, because the read's *shape* does not depend on the live session: a historical-bar pull (a stored time series addressed by symbol + time cursor) or a persistent status board (a standing administrative list that survives across sessions). It is NOT a metadata facet — every candidate carries the same `venue_session: krx_regular` as the session-gated reads — so the call is hand-made and backstopped by the non-empty-assert-before-record gate (a wrong guess dispositions to pending, not a false flip). Contrast: live quotes/order-books/expected-index reads return empty `00707` under closure and must wait for an open window. A non-obvious third case is an account *capacity/deposit computation* read (margin order-quantity, provisional-settlement deposit, balance valuation): it returns a deserializable non-empty row whose every substantive field is zero — a non-flip that does not look empty — unless the account actually carries margin/F-O funding. Only stored cash-summary and reference reads (deposit `sunamt`, a loanable-stock list) are closed-window reachable in the account lane.

### Holdings gate
The pattern that determines whether the paper account holds securities/positions before any positions-dependent read is queued for a flip: model the holdings TR first (e.g. `t0424`) and read its position out-block array *length* from the typed smoke — not the raw-probe `body_len`, which a cash-summary block always inflates. An empty array on a non-default cash summary means cash-only; that single determination *cascades*, downgrading the whole positions/F-O cohort to expected-empty so their all-default smoke results are predicted, not surprising.

### Credential lane
A per-account paper credential set — `(apikey, secret, account_no)` — selected for a request by the TR's `instrument_domain` facet (`stock` → domestic, `futures_options` → domestic-option, `overseas_stock` → overseas, `overseas_futures` → overseas-option). It exists because the LS gateway resolves the target account **entirely from the OAuth token**, never from the account number on the wire: dispatch sends only `tr_cd`/continuation/content-type/bearer-token, and LS's account-read request bodies carry no account field. So one appkey reaches exactly one account, and reaching a different account requires a different appkey, not a different number. A read that returns empty `00707` may simply be authenticating as the wrong account (a wrong-lane artifact) rather than carrying no data — distinct from the genuinely-unfunded case behind the [[Holdings gate]]. A lane whose credential file is absent **fails fast** rather than falling back to another account — a silent fallback would reintroduce the wrong-account hazard (see [[offline-makefile-guard-test-via-real-recipe-shim]] for the guard's regression net).

### Focused Evidence
A recorded, credential-free result of a Paper Live Smoke that backs a Recommended TR's claim. A smoke run gates Implementation; it only becomes Focused Evidence when a TR is deliberately promoted to Recommended.

### Provisionality Ledger
The repository-level sidecar that records, per TR, which authored facets are still provisional and what must be re-verified before promotion. Rows retire as a TR is implemented and each facet is confirmed against a live call; a pending or held TR keeps its rows so nothing is silently treated as confirmed.

### Position manufacture
The order-placing act of creating the account state a positions-dependent read needs to certify: a 1-lot marketable F/O buy that fills, witnessed by a non-default signed balance row, then flattened fail-closed by an opposite-side marketable close. It exists because the paper account is funded but historically position-less, so the read's [[Paper Live Smoke]] can never see data without first manufacturing it. Always operator-run in an open window, never autonomous; the harness's preflight flat-gate refuses a non-flat book, and its teardown engages the kill switch only after every close attempt ([[Pending]] on refusal arms, loud fail-closed panic on an unflattenable position). Contrast the order-chain smoke, which rests unfillable at the daily limit precisely to avoid creating a position.

### Reopen trigger
The concrete external event a [[Pending]] or HELD TR's disposition names as the thing that would make a flip attempt worthwhile again — a manufactured/funded account state, a specific session window (after-hours, an open overseas window), a live data event (an `NWS` news frame), or a gateway-side fix. Once a residue pool is terminally dispositioned, further window time is spent *executing an armed trigger*, never re-probing the pool. A trigger is **armed** when everything it needs short of the event itself is already staged (harness, smoke target, lane creds), so the flip is metadata + docgen only when the event lands; a trigger requiring an out-of-band operator action (an LS-portal deposit, a watchlist registration) is unarmed until that action happens.

### Pending
A TR whose Paper Live Smoke ran but did not open the Implemented gate — callable yet shape-unconfirmed (empty result), or blocked by an unresolved input or an environmental gateway rejection. A pending TR ships without flipping to Implemented and keeps its provisional ledger rows. Distinct from [[Paper-incompatible]]: a Pending TR is expected to flip on a recovering re-run, where a Paper-incompatible TR never flips on paper.

### Paper-incompatible
A TR the paper gateway will never serve, so it is recorded as a permanent non-flip (the `paper_incompatible` facet) rather than a re-runnable [[Pending]]. *Avoid:* paper-unavailable.

Three terminals reach this status, distinguished by the gateway signal: a hard *service-rejection* (the gateway rejects the read outright in any window), an *account-incapable* rejection (the operation needs a paper account the current one is not provisioned for — per-account, not per-service, so it recovers once such an account exists), and an in-window *feed-unprovisioned* empty (a clean success with no data even inside the correct session window — the disambiguating test against an off-window empty, which is a session-clock timing miss and merely [[Pending]]). The `paper_incompatible` facet is a documentation/routing flag meaning "won't flip on paper"; it does **not** imply the runtime paper-incompatible classifier fires — that classifier is bound to the service-rejection code only, and stays silent for the feed-unprovisioned terminal.

## Adapter data

Vocabulary for the standalone Nautilus adapter's market-data catalog (`adapters/nautilus/`).

### KRX trading-date status
The calendar judgment for a Korea Exchange domestic-equity regular-session date. It has three distinct outcomes: **Trading Session** when official evidence proves the session exists, **Closed** when official evidence proves no regular session exists, and **Unknown** when the maintained evidence does not cover the date. Unknown is never treated as Closed; each consumer applies its own safety posture to missing evidence.
*Avoid:* business day (includes non-exchange weekdays), holiday status (does not express positive sessions or missing evidence), boolean trading day (collapses Closed and Unknown).

The three outcomes are **not symmetrically provable**, and that asymmetry is deliberate. Closure is provable *forward*: weekends, published holidays, and cited exchange closure notices can all be asserted before the date arrives. A Trading Session is provable only *backward* — it requires observed evidence that the venue actually operated, which does not exist until after the day has traded. Consequently the **current** date reads Unknown for its entire duration, including the whole live trading morning, and refreshing the evidence does not change that. Unknown on today is the normal operating state, not missing data or staleness; a consumer that must act on the current day needs an [[Attended Unknown override]] rather than an inference. Inferring a session from "weekday and not a holiday" is specifically excluded: it would let an unproven venue closure read as a green trading day.

### Attended Unknown override
The narrow, audited authorization that lets a consumer proceed on a date whose [[KRX trading-date status]] is Unknown. It is bound to one exact trading date and one run, carries an operator identity, a reason, and a structured first-party citation, and is refused unless the run is attended.

It authorizes the run; it does **not** change the day's status, and no belief about the date enters the calendar. It applies only to Unknown — a proven Closed is never overridable, and neither is an unavailable calendar, because both are *proven* states rather than unproven ones. Being bound to a single date and run, it is never a standing waiver.

### Derived window state
The moment-level judgment a "what now" surface derives for the current instant, composed from the [[KRX trading-date status]] and the preserved 09:00–15:30 KST intraday window: **known-closed** (a proven Closed date, or outside the intraday window), **presumed-open** (today reads Unknown retrospectively but is within snapshot coverage, is not a proven closure, and the clock is inside the intraday window), and **genuinely-unknown** (calendar unconfigured, unavailable, or the date outside snapshot coverage — fail closed). Advisory only: presumed-open orients an operator toward attended work; it never authorizes a run — authorization on an Unknown date still requires an [[Attended Unknown override]].
*Avoid:* open/closed boolean (collapses presumed-open and genuinely-unknown), session status (that is the day-level [[KRX trading-date status]], which stays Unknown all of today by design).

### Calendar Adoption State
The per-consumer rollout posture for the shared offline KRX calendar. It was a staged progression — **Legacy** (calendar not consulted, pre-existing weekday/civil-date arithmetic), **Shadow** (compute + record the calendar's [[KRX trading-date status]] decision to a non-persisted channel while the legacy weekday path stays authoritative, byte-identical to Legacy), **Enforced** (the calendar decides with no weekday fallback) — advanced independently at each calendar-dependent boundary. With the #189 weekday retirement (closed) all four consumers reached **Enforced** and the `Legacy`/`Shadow` scaffold was removed (U10): **Enforced is now the sole surviving posture** and the `LS_CALENDAR_ADOPTION` env resolves only `enforced`.
*Avoid:* feature flag (the retired progression was a three-state Legacy→Shadow→Enforced rollout, not a boolean on/off), rollout percentage (adoption was per-consumer, not per-request).

### Calendar Foundation Gate
The shared offline gate that must pass before *any* weekday-era workaround is retired: the entire calendar-core, refresh, diagnostic, six-consumer, composition-root, and fixture test surface plus the standalone adapter workspace gate pass entirely offline — fixed clocks, no production snapshot, no credentials, no network access, no real KRX-derived rows, no wall-clock dependence. It proves the calendar machinery is trustworthy; it does not by itself authorize cutting any specific consumer over to [[Calendar Adoption State|Enforced]].

### Consumer Retirement Gate
The per-consumer gate that authorizes removing *that* consumer's legacy weekday path and cutting it over to [[Calendar Adoption State|Enforced]]. Required in addition to the [[Calendar Foundation Gate]], plus an owner-local canary, a restart after activation, and a rehearsed rollback — all operator-attended and live, so they sit outside the offline slice. All four gates (ingest, catalog, budget-probe, Ladder) fired and are recorded `PASS` (issue #189, closed); each consumer's weekday primitive and the shared scaffold were then removed. While a gate was still pending, that consumer's weekday primitive stayed in the tree and Shadow remained its authoritative path.

### Genesis snapshot
The first real snapshot in a calendar's predecessor chain: predecessor-less (`predecessor_artifact_id` absent), non-synthetic, built from real evidence through the production candidate machinery, and installed by a first-install activation that applies the full approval ceremony with only the stale-base check waived (a chain root has no predecessor to match). Everything after it is an ordinary refresh: successors always carry the installed active's artifact id as predecessor. Distinct from the synthetic seed fixture and test-helper snapshots, which are also predecessor-less but marked synthetic and never installable.
*Avoid:* bootstrap snapshot (ambiguous with the unrelated dispatch-chain genesis in the lab subsystem — qualify as *calendar* genesis where context is unclear), initial fixture (the seed fixture is synthetic and is not a genesis snapshot).

### Witness
The one evidence class that can prove a date **was** a trading session: an observation that the exchange actually published that day's market data. It is asymmetric with the calendar's other evidence — a holiday table and a weekday rule can prove a date *closed* forward in time, but neither can establish that a session happened, so only a witness moves a date from `unknown` to trading-session. Two consequences follow. A date can only be witnessed *after* the exchange publishes it, which is why the current day always reads `unknown` while you are standing in it. And a refresh whose witness-bearing source failed while its rule and holiday sources succeeded looks two-thirds healthy and establishes nothing — it yields a candidate marked partial with no new trading days, in which every date you refreshed for still reads `unknown`. Check the rows, not the summary, before treating such a candidate as an improvement.

### Forward readiness
The calendar's claim about the *future*: the date through which scheduled closures have been evaluated, so consumers can ask "is date D a session?" for D ahead of today and get an answer rather than `unknown`. It is a freshness dimension, not a coverage one — coverage says which dates were materialized, forward readiness says how far ahead the closure question was actually asked. The two are stamped equal at a [[Genesis snapshot]] and then diverge, because the horizon decays simply by the passage of time: every day that elapses shortens the remaining runway until the snapshot reads stale. Stale is **usable by design** — the loader accepts it, and a stale forward horizon does not bound a query about a historical date, only one about a forward date. Advancing it is a refresh cadence, and the claim is only as good as its evidence: it may move forward only over a span the holiday and rule sources actually covered, since a source reporting success is not the same as a source having *checked* the dates being claimed. Contrast the [[Witness]], which is the asymmetric evidence class for the past — no witness can establish a forward date, which is why the exchange's own daily-market source is exempt from evidencing a forward span.
*Avoid:* calendar freshness (the snapshot carries several independent freshness dimensions; forward readiness is only the forward-looking one), coverage horizon (that is materialized coverage, a distinct field that can sit ahead of forward readiness).

### Accumulate-forward
The adapter's checkpoint-driven ingest mode: per `(instrument, bar type)`, a watermark records the last closed session date whose bars are covered, and each run grows coverage from watermark+1 to the last closed session (or from the bounded backfill floor for an unseen instrument). The watermark is the sole skip authority. Coverage grows only through the contiguous run of calendar-established days: the plan stops before the first `unknown` day and never crosses it, so one unwitnessed day caps every symbol's advance — however many established sessions lie beyond it — until the calendar establishes that day. Under the Enforced calendar (post-#189) it advances over a **proven Closed** day (a holiday/weekend the calendar attests) but **does not advance over an empty proven Trading Session** — a session the calendar proves open that serves zero bars pins the watermark before it, so the triple is conservatively re-fetched on the next run rather than marked covered with zero bars. A persistently-empty proven session — a multi-day halt or a listed-but-non-serving symbol — would otherwise be re-fetched on *every* invocation at the same target, and because the per-symbol drip re-invokes the binary many times per dispatch cycle that repeatedly charges the cumulative [[Rolling call budget]] (`IGW00201`); that retry is **bounded** (`LS_INGEST_EMPTY_RETRY_MAX`, default 3): after N consecutive runs where the frontier proven session serves zero bars, the triple **converges** — it records a documented `EmptyHistory` gap (never coverage — the watermark still does not advance) and skips the gateway call for further runs *at the same last-closed target*. It **re-arms** when the target advances (a later closed session may serve bars, so it retries at most once per new session), and **resets** when it serves bars or its watermark advances. Convergence is *skip*, not *cover*: the conservative posture is preserved, merely capped so a persistently-dead triple stops re-charging the budget on repeated same-target runs. Idempotent by construction — re-running covers nothing twice — but only within the watermark format: the watermark records a last covered date with no representable coverage start, so a checkpoint predating the format (legacy `completed` ranges, empty watermarks) shares no coverage state with it, and widening such a catalog re-fetches from the floor and writes overlapping duplicates.

### Adjustment-basis splice
The corruption an appending catalog accrues on an adjusted-price basis: the gateway rewrites the entire adjusted series at every split/dividend, so bars accumulated before a corporate action sit on a different price basis than bars appended after it. The spliced series shows an overnight discontinuity that a gap/stocks-in-play scanner misreads as signal. Detected per symbol by [[Accumulate-forward]]'s overlap re-fetch and reported per run as the set of affected symbols — never as a catalog-wide flag.

### Catalog re-base
Rewriting catalog bar history wholesale to restore a single price basis (after an [[Adjustment-basis splice]]). By design it may rewrite the catalog tree entirely but must never touch `runs/` — run history lives outside the catalog tree precisely to survive a re-base — and an in-flight backtest is protected by its in-range catalog-fingerprint abort. The one-time whole-catalog form is an **epoch re-base**: mark every symbol shifted, then heal each through the same per-symbol path, making the epoch crash-resumable by construction.

### Basis-shift heal
The per-symbol [[Catalog re-base]] triggered when accumulate-forward's overlap re-fetch disagrees with stored daily bars: durably mark the symbol shifted, true-delete its daily series, clear its watermark, re-pull from the bounded floor, re-verify, then clear the mark and record a re-base event. The mark outranks the watermark as authority and re-entry always restarts at the wipe, so an interruption at any step converges to the same path. Detection compares only mutually-present non-gap dates (exact integer match) and skips symbols with insufficient overlap. A re-pull that completes with zero rows counts as completion only for a series that was already empty before the wipe — for a previously non-empty series the heal stays incomplete and the mark is kept, because an empty page from the gateway is a transient-source signal, never proof of absence.

### Suspect partial
A page-walk termination that is not proof of completion: a zero-row page whose echoed body cursor is still live, or a re-served (echoed) page. Either fails closed — the chunk surfaces as incomplete, splits, and bottoms out as a recorded coverage gap that withholds completion — because reporting it clean would mark a silently truncated range done with zero gaps. Only an exhausted [[Body-cursor continuation]] cursor completes a walk cleanly; the echoed duplicate page's rows are never ingested. Kin to [[Basis-shift heal]]'s rule that an empty gateway page is a transient-source signal, never proof of absence.

### Universe metadata pin
The catalog-level attestation binding ingested bars to the reference-data artifact that selected them: a pin file (`universe-metadata-pin.json` in the catalog root) recording the artifact's content hash and per-stratum selection, written **only after a refusal-free tier-stratified ingest** (exit 0 — any range/heal/append refusal withholds it, because a pin written despite failure would attest a selection whose bars never landed). Consumed as a three-way hash handshake — pin == run-manifest `universe_metadata_hash` == artifact-on-disk — asserted fatally by the metadata-driven backtest runner on mismatch and by the per-tier report on mismatch *or absence* (the runner alone only warns when no pin exists yet). Never hand-written or copied; a scratch/rehearsal artifact's hash must never be pinned.

### Mount universe
The per-session candidate file an attended session consumes: for one session date, each catalog symbol's prior-session facts (close, ATR, opening-volume mean, illiquidity) plus that day's open — sourced from the catalog for a past date and from a live opening quote for the current date. It is the candidate *set*, not the selection: the head's gap floor, turnover ranking, and top-N run at selection time against these rows, so the file legitimately carries rows the head will not trade, and an empty *selection* on a market-wide flat open is normal head behavior. The producer refuses to write an empty file, and the file is never hand-authored — a row missing its prior ATR silently disables a protective per-symbol gate rather than failing loudly.

## Order safety

The order class is the one place where a bug is a real, irreversible market action rather than a stale read, so it carries its own machinery and vocabulary.

### Double fill
The cardinal order-class failure: the same order placed twice at the exchange. The whole order-safety package (no-retry dispatch, the deduplicator, reconciliation) exists to make a double fill structurally hard. Its asymmetry drives the design — a false "already done" is harmless (reconcile and skip), a false "not done, safe to retry" causes the irreversible second fill — so every order guard fails toward the not-safe conclusion.

### Ambiguous order outcome
An order send whose result cannot be proven Accepted or Rejected: a transport timeout / 5xx (other than a gateway ingress-validation reject, see below), or an order acknowledgement carrying the generic-success code (`00000`/empty) that — unlike a read — does not prove acceptance. Because dispatch is no-retry, an ambiguous outcome is surfaced (as `LsError::AmbiguousOrder` or a transport error) and resolved by [[Order reconciliation]], never blindly retried. Distinct from a clean rejection (a recognized broker reject code → `ApiError`) — which **includes an ingress-validation reject (`IGW40011`, a numeric request field sent as a quoted string): it arrives as `http=500` but the gateway refuses it before routing to the exchange, so it placed nothing and is classified `ApiError` (Reject/placed-nothing), never may-rest.** Not to be confused with the rate-limit throttle (`IGW00201`), which stays may-rest. Classify an order failure by whether it could have *rested*, not by its HTTP status (see docs/solutions/logic-errors/igw40011-ingress-reject-is-placed-nothing-not-may-rest.md).

### Order reconciliation
The post-ambiguity resolution: query the order/execution read (`t0425`) for the symbol, match candidate rows against the local intent (by order number, else symbol/side/quantity/price), and classify the outcome into one of six states — Accepted, Rejected, Duplicate, Modified, Canceled, Unknown. A retry is authorized only when a *complete* query proves no matching order was accepted; a failed or truncated query, or a degenerate match key, fails toward Unknown + not-safe. Reconciliation is **action-aware**: a submit asks "did a new order appear?", while a modify/cancel references an *existing* order by its original order number and the matcher scans **all** rows for the strongest classification (a `취소`/`정정`/`거부` transition outranks a still-received original). A modify is idempotent-by-target (a rejected modify is safe to re-send); a cancel inverts the risk (see [[Inverted cancel risk]]).

### Inverted cancel risk
The cancel-specific direction of the [[Double fill]] asymmetry: where a submit's danger is placing a second order, a *cancel* wrongly believed to have succeeded leaves a **live resting order** in the market. So [[Order reconciliation]] for a cancel classifies Canceled only on explicit proof (a `취소` row for the referenced order); every other observed state — still-resting, modified, or even a cancel-rejection — fails toward "still-live", never assumed canceled, and never clears the retry guard. At the order class's Implemented flip this path stays mock-proven only (a clean [[Guarded paper order]] run never produces an ambiguous cancel against a genuinely live order).

### Guarded paper order
The order class's Implemented gate — a paper-only evidence matrix (a resting far-from-market buy and sell, one marketable order, one deliberate rejection) that pins the order success predicate from observed real broker codes. It replaces the read class's [[Paper Live Smoke]] (the automated gate never submits a live order) and the realtime class's lifecycle gate. Originally operator-initiated; the chained variant is now **agent-invocable** under a fail-closed autonomy precondition (a CI/no-TTY refusal plus a fresh per-wave human nonce) — autonomy removes the operator-handoff *protocol*, not the human, and pairs with an [[Account-flat assertion]] as its post-run safety net. If the paper account cannot place in-window, the run records [[Pending]] and the order TRs do not flip.

### Account-flat assertion
The post-run safety net of an autonomous [[Guarded paper order]] run: after the submit→modify→cancel teardown, a `t0425` working-orders scan must positively confirm zero live rows. Because no operator remains to clean up, it keys on quantities not status text — a fill (`cheqty>0`) is unrecoverable (hard-fail, paper reset), a resting remainder (`ordrem>0`) is retry-canceled then hard-failed if it persists, and a cancel-rejected (`취소거부`) order is treated as still-resting despite its 취소 marker. Positive-confirmation-only: a failed/timed-out/**truncated** read is NOT flat — it fails closed on a pagination-continuation signal rather than trust a partial page. Originally an account-wide all-states scan (to catch a prior-run leftover on any symbol); on a heavily-used paper account that exhaustive walk overran the gateway's `t0425` page cap and never completed, so it is now **scoped to the traded symbol and to working (unfilled) orders only**, read as a single page. That scope is sound because the chain trades exactly one symbol at non-marketable prices that cannot fill — it still catches a still-resting order and a partial fill (both carry unfilled remainder) and only forgoes detecting a *fully*-filled or other-symbol row, which the chain cannot create. An [[Ambiguous order outcome]] on the submit leg routes through it rather than recording a silent [[Pending]]. Bounding it required pacing around an LS `t0425` rate-throttle (`IGW00201`) whose per-TR 2/s cap is tighter than the SDK's market-data rate bucket (see docs/solutions/integration-issues/ls-gateway-t0425-rate-limit-and-pagination-flat-scan.md). The form above assumes an Implemented working-orders (미체결) read; a venue lacking one (the domestic **F/O** chain) cannot scan the board, so its flat assertion is **two-part**: a `t0441` balance read detects a *filled* position only (잔고; empty/unreadable = NOT flat, and a short/negative position counts as a fill via `f64 != 0`), and a **clean cancel response** is the only confirmation the resting order was removed. With no board read to verify removal, ANY teardown-uncertain state — an accepted submit returning no order number, an ambiguous modify, or a non-clean cancel — hard-fails rather than concluding flat (see docs/solutions/conventions/authoring-fo-order-tr-chain.md §5).

## Strategy loop

### Strategy-improvement loop
The development model for trading strategies on the Nautilus adapter: collect data ([[Accumulate-forward]] plus bounded backfill) → backtest → an agent analyzes the run's artifacts and produces an improvement analysis → a strategy change lands → re-backtest, compared to the prior run via manifests. The loop, not any single strategy's quality, is the product; starter strategies exist so the loop has something real to improve. Live paper sessions join the loop as just another run — same artifact set, same [[Run registry]], with fidelity caveats flagged rather than fixed.

### Run registry
The append-only store of strategy-run records. Every run — backtest or live paper — deposits the same four agent-readable artifacts: a performance report (fills, per-trade P&L, equity curve, summary stats), a per-decision envelope stream (`decisions.jsonl` — every candidate evaluated, the decision, and the rejecting filter/signal values), a data-quality report (coverage gaps, adjustment-basis splice flags, and for live runs any reconcile-advised conditions), and a run manifest (strategy version, full parameter set, data range, catalog state) that makes any two runs comparable and any run reproducible. Runs are never overwritten; improvement analyses are stored alongside the runs they analyzed.

### Latest finalized run
The newest completed record in the [[Run registry]], and the loop's single authority for "current": a governed parameter turn resolves the parameters it proposes from — and its guardrail measures relative change against — the latest finalized run's manifest, regardless of which older run an operator happens to be inspecting. Any tool that previews a governed decision while reading a different run must either share this anchor or state the divergence explicitly, because a verdict computed off an older run's parameters can flip against what the governed turn will actually decide.

### Strategy lab
The crate that houses strategy code, the backtest and live-paper runners, and the artifact writer — deliberately separate from the certified adapter crate, whose contract is translation only. The [[Strategy-improvement loop]] exists to generate strategy churn, and the lab boundary keeps that churn from destabilizing the adapter.

### Paper-cut log
The committed friction log the [[Strategy-improvement loop]]'s operator or agent maintains: each entry is an observed workflow friction framed as a candidate requirement for the deferred research CLI, with enough context to act on without re-running the cycle. Credential-free by construction and linked from the lab recipe so an agent discovers it before turning the loop; defects fixed in-flight stay in the log with their residual owner named.

### Merit-bearing turn
A [[Strategy-improvement loop]] turn whose run produced real fills for the analysis to reason about — trades > 0 — and whose analysis reaches an explicit, evidence-grounded verdict on the change: keep, revert, or insufficient-evidence. Positive P&L is NOT part of the bar: on a thin sample any expectancy number is noise, and requiring profitability would push the loop toward overfitting its first real data. The loop's product is decisions, so a clean "revert — sample too thin, widen the slice" verdict is full merit. Contrast: the zero-trade baseline turns before it, which prove the machinery but give the analysis nothing to judge.

### Composed data turn
A loop turn that changes the data rather than a parameter — a wider ingested slice (more symbols or days) — executed by composing existing pieces (ingest, catalog inspection, backtest, manifest compare) rather than through the parameter-turn envelope machinery. Its manifest delta is *explained* (the universe/range change acknowledged under the comparison verdict's equal-or-explained clause) instead of param-isolated; it does not get first-class envelope support until the shape has been exercised more than once.

### Param-turn governance
The two refuse-and-run-nothing guards a parameter [[Strategy-improvement loop]] turn passes before a backtest runs. **Proposal-bounds cap:** a single turn may change a parameter by at most 50% relative to its current value (a committed constant, not operator-overridable); a larger intended change is reached through multiple legged turns, each within the cap. **Seed-assertion:** the turn asserts the resolved base strategy identity (version + gap seed) before running, so it cannot silently drift from an unexpected base — on a fresh [[Run registry]] with no prior run it refuses rather than fall back to default parameters. Together they keep the loop's evidence chain from being corrupted by an oversized jump or a wrong-base run. A param turn's verdict is a keep/revert/insufficient decision on a single knob; it never edits strategy code — contrast the [[Strategy-logic turn]].

### Strategy-logic turn
A loop turn that changes the strategy's *code* rather than a parameter or the data — adding or altering entry/exit logic such as a profit target, trailing stop, or breakout-strength filter. It is the third turn type alongside a parameter turn (see [[Param-turn governance]]) and a [[Composed data turn]]. Because it edits code it bumps the strategy's code hash and **re-baselines** the loop (the new strategy version becomes the base for subsequent runs), so it sits *outside* [[Param-turn governance]] — its outcome is a re-baseline, not a keep/revert verdict on one knob. It is the correct escalation when no parameter knob can move the metric that matters: e.g. when a knob raises win rate but expectancy stays negative, the residual lives in payoff/exit geometry, which only a strategy-logic turn can change.

### Mechanism-harness turn
A [[Strategy-logic turn]] whose code change *adds* new mechanisms as parameterized, default-off gates rather than activating any of them. Its baseline run with every gate at its filter-off default must reconcile to the prior baseline's ledger — a divergence is a harness defect, not a finding. Because new params carry serde filter-off defaults, pre-field manifests deserialize identically and produce no param diff, so the code hash re-baselines exactly once and each mechanism thereafter activates as a seed-and-rerun single-param turn — the governed numeric proposal path cannot move a param off an exactly-zero or sentinel default (guardrail fail-close + the 0.5 cap), so the new value rides the seed manifest and attribution comes from the param-mode compare PASS with a one-param diff — per-mechanism attribution without one re-baseline per mechanism. Its gates are consumed by a [[Lever queue]]; a gate never flipped by the time the queue is exhausted is removed (wire-or-delete), because dead config is a documented recurring defect in surveyed strategy codebases.

### Lever queue
An evidence-ranked backlog of candidate strategy mechanisms consumed one governed turn at a time — ranked by diagnostic fit to the observed failure signature first, external field consensus second, implementation/data cost third. After every verdict the queue is re-ranked before the next flip: a falsification is evidence about sibling mechanisms (a falsified entry-quality gate demotes the other entry-quality gates), not just a pop of the head. A mechanism whose data prerequisite the lab lacks stays queued as *blocked-on-data* with the prerequisite named rather than being silently dropped.

### Breakout strength
How far beyond the opening range a breakout fired, in R-multiples: `(breakout_price − range_high) / R` with `R = range_high − range_low`. Computed per trade by joining an exit envelope to its breakout envelope, so it is readable from any run's decision stream without re-running the strategy. Its relationship to expectancy is **non-monotonic — a band-pass, not a threshold**: turn 9 found the middle band (≈0.067–0.125) the only positive bucket under all three exit geometries, while both marginal breakouts (too weak) and overextended pops (too strong) carry the losses. This makes it an entry-side filter axis for a [[Strategy-logic turn]], distinct from exit-side levers read via [[MFE (maximum favorable excursion)]].

### Opening-Range Gap-Retention Fraction
An entry-filter observable measuring how much of a positive overnight gap survived the completed opening range: `retention = (opening_range_low − prior_close) / (today_open − prior_close)`, computed on canonical integer KRW/tick prices with only the final ratio as `f64`. `1.0` is full retention, `0.0` is a prior-close touch, negatives stay signed (a crossing below the prior close), values above `1.0` are invalid data; the observable applies only when `prior_close > 0` and `today_open > prior_close`, and it freezes at the end of the half-open opening-range window, before the first post-range bar is evaluated. Governed by the manifest param `gap_retention_min`, whose `1.0` value is reserved exclusively as OFF (the only inverted sentinel among the lab's default-off gates); the sole armed cutoff is `0.50`, equality passing, evaluated once as the final ORB session gate after the ATR, opening-range-width, and RVOL gates.

### MFE (maximum favorable excursion)
The per-trade best unrealized gain, expressed in R-multiples of the opening range: how far price moved in the trade's favor between entry and exit, regardless of where the exit actually landed. Recorded on every exit envelope in a run's decision stream so exit-geometry tuning reads give-back (MFE achieved vs. profit realized) directly from data instead of reconstructing it. A trade stopped out at −1R with an MFE of +1.2R gave back a winner; a distribution of MFEs across a run tells an exit-tuning turn where a profit target should sit. Zero before entry or when the opening range is degenerate.

### Return-on-risk (RoR)
The risk-weighted keep crux for a sizing/position-risk lever: total realized P&L divided by total deployed stop-based risk capital (`Σ realized_pnl / Σ risk_capital`, where a trade's risk capital is its quantity times its entry-fixed stop distance `entry − stop`). Unlike per-trade KRW expectancy — which a uniform size-up inflates with no better edge — RoR is invariant to uniform scaling and moves only when a lever **reallocates** risk across trades, so it is the metric a pure sizing lever is judged on. Its denominator stays stop-based even when a lever sizes on a different basis, so successive turns compare on one metric.

A sizing lever KEEPs only on a deterministic strict inequality — RoR strictly above the current head's — **and** `is_edge`: positive expectancy with **risk-capital dominance** (the largest single symbol's share of `Σ risk_capital`) under its cap. Equal-weight mean-R rides along as a size-invariant diagnostic that a pure reallocation leaves unchanged. A second sizing axis cannot move RoR in two ways: when it is **collinear** with the axis the kept lever already sizes on, or when it is **near-constant** across trades (nothing to reallocate — a failure mode a collinearity check alone passes trivially). Either way the lever is predicted **INERT**, and the strategy loop's convention is to gate such a second lever on a pre-code check before building it — a collinearity gate plus a **materiality gate** on the new axis's dispersion (see docs/solutions/conventions/pre-code-collinearity-gate-before-a-second-normalizer-lever.md).

### Additive entry stream
A [[Lever queue]] mechanism that adds a NEW set of trades layered on the current head (the [[Latest finalized run]]) rather than re-weighting or conditioning the trades it already takes — the head's decision stream contains none of the new stream's trades. This structurally changes its screen: with no incumbent per-trade signal to correlate a candidate weight against, its pre-code screen **drops the collinearity gate** a sizing/tilt lever is judged on (see [[Return-on-risk (RoR)]]) and gates instead on a pre-registered population-count floor plus an *additive* RoR shift — the head-plus-stream RoR minus the head's, both re-simulated on one common baseline so pessimistic-fill bias cancels. The scored population is an unconstrained upper bound: the stream draws from the head's shared position-slot and risk-budget capacity, so displacement of existing trades and slot starvation shrink the realized population, visible only when the stream is actually armed. Contrast a re-weighting lever (a tilt or condition on existing trades), which keeps the collinearity gate because an incumbent axis exists to correlate against.

### Exit-geometry lever
A [[Lever queue]] mechanism that re-parametrizes the head's EXIT timing — profit target, breakeven trigger, time-exit, stop mode — on the trades it already takes, rather than re-weighting their size ([[Return-on-risk (RoR)]]) or adding new ones ([[Additive entry stream]]). Because it reallocates *when a trade books*, not the risk budget, it has no budget axis to be collinear with, so its pre-code screen **drops the collinearity gate** and gates instead on **direction** (a signed RoR delta — the size-invariant RoR re-booked at the new geometry minus the head's, which must strictly improve) plus **materiality** (the fraction of trades whose booked outcome changes). The counterfactual re-books each trade from telemetry — [[MFE (maximum favorable excursion)]] against the new target — never a bar replay, and is one-sided (a profit-target lower fills at or above the new target on a gap-through), so it under-states the flip's edge: a STOP is a robust NO-BUILD, a GO only necessary. Contrast an [[Additive entry stream]] (drops collinearity because no incumbent per-trade signal exists; this drops it because no risk-budget axis exists) and a sizing/tilt lever (keeps the collinearity gate).

### Ratio-axis collapse trap
The failure mode where a dimensionless sizing axis (e.g., `ATR/price`) silently reduces to the absolute axis it was built to escape: if the ratio enters a KRW-denominated sizing formula multiplied back by price — `budget / (k · (ATR/price) · price)` — price cancels and the lever is absolute ATR again, which is collinear with the stop-based denominator and predicted INERT (see [[Return-on-risk (RoR)]]). The anti-collapse rule: a ratio axis may only enter sizing as a **dimensionless multiplier on the budget numerator** (`qty = floor(budget · w(ratio) / risk_per_share)`), never as a component of the risk denominator. Because any monotone `w` preserves the ratio's rank correlation with `risk_per_share`, the numerator-only shape keeps the new axis's collinearity reading at the raw ratio's Spearman bound.

### Power pre-check
The counts-only staging gate between a universe-composition turn and the per-tier expectancy turn it would power: GREEN when ≥ 30 trades land in ≥ 2 cap/market tiers, read from a metadata-driven count run's decision stream under the [[Universe metadata pin]] handshake. RED is a **valid completion**, not a failure — it calls off the expectancy turn and returns the floor question to the operator. Its staging guard: the count run's `performance.json` is written unchanged but never read for the verdict, so no expectancy number can leak into a go/no-go that is only about statistical power. The count run adopts a pre-registered params identity via params-from-run with an explicit version ack; a companion run under different params may be reported beside it as a non-gating diagnostic, but the verdict reads from the pre-registered run only.

## Production ladder

### Production ladder
The governed path from certified paper trading to full-size live trading: capital escalates through four pre-registered live rungs (minimum size up to the full risk budget) above a rung-0 *suspended* state (paper-only, no live sessions), where advancing a rung requires N clean sessions at the current rung and any [[Limit event]] auto-de-escalates one rung — a rung-1 limit event drops to rung 0, the program's stopping rule. Distinct from the TR support ladder (see [[Support lifecycle|Raw]]) — this ladder governs how much real money a strategy touches, not a TR's maturity. Rung state lives in the dispatch chain: the current rung is whatever the last valid [[Dispatch release]] authorizes, so every capital change carries a hash-chained, evidence-citing record (tamper evidence is the hash chain, not key-based signing — the single-operator threat model is accidental mutation). A red readiness verdict does not deadlock the ladder: it forces the session to rung-1 *probation* — the record carries both the chain-authorized rung and the effective rung (1) so capital history stays reconstructable from the chain alone, and probation sessions count toward no rung's N. The rung fraction that scales the risk budget is a runner-threaded, numerator-only multiplier, never a strategy/manifest param, so a rung move leaves [[Head identity]] unchanged.

### Head identity
The certified-strategy fingerprint every live capital action keys on: a hash over the strategy's decision source paired with a hash over its governed params, pinned to an expected strategy version. Mounting a session, escalating a rung, and reporting session cleanliness all resolve the head by matching the running binary's fingerprint against a finalized run's recorded one.

The code half is scoped to the decision source *file*, not to the strategy's behavior. Any edit to that file moves head identity — including one that provably cannot change a backtest, such as live-only wiring threaded through the strategy for a runtime supervisor to read. This is deliberate: an exemption for "inert" edits is the mechanism by which an uncertified strategy would reach a live account. The consequence is that the ladder must be re-baselined — a fresh run at the *same* strategy version carrying the new fingerprint — before it will mount again, and by the frozen head-change rules a code-side move is a head-change event that returns the ladder to its first rung. Resolution is fail-closed rather than fail-open: when nothing matches, the head collapses to the all-levers-off default, whose zero risk budget would size every order to zero shares, so a zero-size guard refuses the mount instead of letting a session trade nothing silently. Runner, config, and rung-fraction changes leave it unchanged by design (see [[Production ladder]]).

### Mount universe file
The resolved set of symbols an attended live session trades, and the one input the mount does not compute for itself: mounting runs no selection, so this file *is* the session's tradable set and is therefore part of the head's behavioral surface rather than a convenience. Every row carries the session date it was resolved for, so a file built for another day is refused rather than silently traded at yesterday's symbols and opening prices. Its optional-looking fields are not uniformly optional — a row missing its prior volatility measure does not fail, it silently switches the armed opening-range-width gate off for that symbol and emits no reject record, so the producer drops such symbols instead of emitting them un-gated. It is produced by reusing the backtest's own selection and volatility helpers, because a parallel implementation would be a [[Head identity]] divergence no gate could catch, and it is refused outright when the head was built from a [[Universe metadata pin|universe-metadata artifact]] that the caller does not supply. Its prior-session values always come from the catalog, so ingest must be current through the previous session; the session date's own opening price cannot be, because [[Accumulate-forward]] will not write a bar for a session still in progress — so for a same-day resolve that one value is read from a live quote instead, the producer's only outbound call. Because the opening price is an input to selection and not merely an emitted field, a quote taken before the opening auction has printed would resolve the whole file against the previous session, so a same-day resolve is refused until the market has opened.

### Dispatch release
The machine-checked pre-flight a live session must pass before mounting: `lab-live --dispatch` verifies every session precondition (advisory lock, lane env, session window, watermark freshness, flat-start, kill-switch state, stranded orders, gateway budget headroom, readiness verdict) and appends a record to the append-only, hash-chained dispatch chain (`dispatch/chain.jsonl`, beside the [[Run registry]] — a refused dispatch produces no run dir, so the record cannot live in per-run artifacts) naming per-check outcomes, any deferrals, and the rung being authorized. A red check aborts unless the operator records an explicit per-item, per-session deferral — the aviation MEL pattern: degraded items are affirmatively deferred, never silently tolerated. Fail-closed by construction: an unreadable, truncated, or tamper-check-failing chain authorizes rung 0 — the *corruption floor*, so a deleted chain file can never escape the suspended state — repaired only by an explicit, recorded re-registration (an epoch rollover archiving the defective file content-hashed, never rewriting it).

### Limit event
A session outcome that blocks rung escalation and auto-de-escalates the [[Production ladder]] one rung (a rung-1 limit event drops to rung 0): (a) a non-flat or unproven close, (b) any reconcile-Unknown order outcome, (c) a [[Tracking-error band]] breach (rung 2+), (d) any safety-mechanism firing (kill-switch engagement, dedup hit on a real emission, teardown needing more than one retry, watchdog firing), (e) cumulative P&L outside the rung's pre-registered expectation band (rung 2+ — operational cleanliness alone never authorizes escalation against a bleeding edge), or (f) a live session that never finalizes — a crash or abort leaving `.tmp-` staging residue and no finalized run (residue classification is chain-driven: `.tmp-` matching a consumed live dispatch's recorded run id is the limit event; residue matching no consumed dispatch is not), or its typed successor: a session whose node had to be **hard-stopped** (it ignored its stop request and was abandoned at the driver's deadline), which finalizes normally and so leaves no residue at all — the flag on the run's data-quality report is what carries the signal, and adding it was required precisely because making that failure graceful deleted the residue the scan had been reading. Conservative by registration: a benign-cause watchdog trip still counts; carve-outs require explicit re-registration. Multiple events in one session de-escalate one rung total, with every event listed in the record and a consumed-through watermark so none double-fires.

### Live-session driver
The orchestration that owns a mounted session's lifecycle, because `node.run` owns none of it: it runs indefinitely with no session timer and no market-close stop, and once entered its handles are unreachable. So the driver grabs the node's stop handle **before** `run`, owns a session-duration timer, spins the [[Watchdog envelope]] on its own OS thread, drives `node.run` under a **stop-relative hard-stop deadline** — the stop is a request the node may ignore, so once any party asks for one the node has a bounded grace to return before the driver abandons it (a [[Limit event]], never a clean session); the deadline arms on a driver-owned latch rather than the node's own stop flag, which the node clears on every transition to running — and then, on session end *or* a trip *or* a hard-stop, runs the fail-closed teardown **exactly once**, arbitrated by an atomic one-shot claim both paths contend on (a non-atomic "has it tripped?" read would race and let both tear down), before staging and finalizing. The teardown runs *after* `node.run`'s own graceful shutdown by design: the node cancels and drains, but that is not the sticky kill switch plus positive t0424/t0425 confirmation the gate requires — the invariant is re-asserted at the driver's altitude, not only at the leaf. Its safety acts operate through handles that share exactly one `LsSdk` (one kill switch) and one fill ledger with the node's in-trader client; a separately-built client would halt a different switch and read an empty ledger, both silent no-ops. `node.run` is the single seam never exercised offline — every surrounding seam is.

### Watchdog envelope
The in-process supervisor that makes "attended" a software property rather than a human at a TTY: a dead-man heartbeat timer (fed both by the strategy on every processed bar and by an operator keepalive file's mtime) that invokes the fail-closed teardown sequence on miss, plus a session max-loss breaker over realized P&L (offsetting fills matched against cost basis) and open positions marked at the **adverse edge** — falling back to the position's stop level when the price feed is stale or absent, because a data gap accompanies exactly the fast adverse moves the breaker must catch. Both route through the one teardown seam, whose order is the safety property: stop emission → quiesce in-flight order dispatches → cancel resting → positively confirm flat → **halt last** (the documented kill-switch-after-close ordering). It never *places* a flattening order — halt-last is safe precisely because the teardown is cancel-or-read only; a non-flat close is an abnormal finalize plus an operator reconcile. Supervision is mutual: the session side treats supervisor silence as its own trip condition, sharing the same one-shot claim. Required from the first live rung; unattended operation remains out of scope.

### Tracking-error band
The frozen tolerance on paper-vs-live divergence — fill price deltas, slippage, approximated-fill fraction — measured per session against a paper twin of the same live session. Reported from rung 1 but load-bearing only from rung 2: rung 1's sessions exist to calibrate the band, which freezes via pre-registration before rung 2 — a paper backtest fills at bar prices with zero slippage, so the divergence this band measures has no signal there at all, and a provisional band would encode exactly the unmeasured paper→live error the ladder exists to measure. This is why it must be *live-calibrated* rather than derived up-front, unlike the [[Expectation band]].

### Expectation band
The frozen economic tolerance on a rung's cumulative P&L — a floor (never escalate against a bleeding edge) and a ceiling (a runaway is worth a second look) — checked across the clean sessions that qualify the rung for escalation; a breach is a [[Limit event]]. Unlike the [[Tracking-error band]], it is derived up-front from the strategy's backtest distribution: cumulative P&L is an outcome of the strategy's own decisions, which a paper backtest faithfully reproduces, so the band needs no live calibration. The contrast is a sourcing rule — outcome bands come from the backtest, execution-divergence bands must come from live data.
