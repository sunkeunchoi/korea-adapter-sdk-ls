The Production Ladder — roadmap-as-code

Description
Replace “are we production ready?” with a rung number. Four components, built as one governed framework: (a) an executable dispatch release — a lab-live --dispatch pre-flight that machine-checks every session precondition (advisory lock, lane env file, KRX window, watermark freshness, flat-start, kill-switch state, stranded-order scan, budget headroom) and writes a signed dispatch.json into the run registry, aborting on any red item without an explicit deferral (aviation MEL doctrine); (b) a readiness score computed over the trailing K runs of the registry (teardown outcomes, approximated-fill fraction, data-quality gaps, aborted runs) that lab-live must see green before mounting; (c) a dose-escalation capital ladder — pre-registered rungs (1 share → 10% → 50% → full 299,340 KRW risk budget) where escalation requires N clean sessions at the current rung within a frozen paper-vs-live tracking-error band, and any limit event auto-de-escalates; (d) FOQA-style exceedance mining over decisions.jsonl and the artifact set (reconcile-Unknown count, teardown retries, dedup hits, pacer outliers) as the trend signal feeding (b) and (c). Known open blockers become named rung prerequisites: the SC-primary fill-lane certification (the 2s-per-symbol poll scales linearly against the shared IGW00201 budget), the stranded-position auto-clear, and idea 2 below.
Axis
operations (spans live-execution and orb-strategy)
Basis
direct: adapters/nautilus/lab/src/runner/live.rs:131-148 is a paper-interlock stub — “the full LiveNode session (lock, mount, node.run, teardown, artifact finalize) is not yet wired”; the run registry is append-only but nothing reads it across runs; there are no metrics and no alerting. external: FAA dispatch release + Minimum Equipment List (14 CFR 121.628); FAA/ICAO FOQA exceedance mining; FDA Phase-I 3+3 dose escalation; the practitioner validation ladder backtest → paper → small-live → full size.
Rationale
This is the literal answer to the roadmap question. Every past operational miss in the repo’s history (stranded 3-share position blocking probes, weekend false NO-GO, macOS env-var trap) is a precondition failure a dispatch check would have caught before the session. The registry already produces every input the readiness score needs; the ladder reuses the repo’s strongest muscle — pre-register-before-read — on the one decision it has never governed: how much real money v30 touches. The zero-operator drill (walk the live recipe assuming no human) is the procedure that generates the complete blocker table for rung prerequisites.
Downsides
The largest survivor by scope — it is a program, not a PR, and needs sequencing (dispatch gate first, then exceedance catalog, then ladder). Rung definitions and tracking-error bands require judgment calls that only live small-lot data can calibrate. Depends on idea 2 for the session it gates.
Confidence
85% — every component is grounded in verified evidence and named prior art; uncertainty is in sequencing cost, not direction.
Complexity
High (decomposable into four medium pieces)

Build the LiveNode mounter inside a watchdog envelope

Description
Wire the missing live-session runner — but build it inside-out. First codify the operator’s actual duties as software: a dead-man/heartbeat timer that invokes the already-unit-tested run_teardown sequence on miss, and a session max-loss circuit breaker feeding set_orders_enabled(false) (respecting the kill-switch-after-close ordering rule). Then the mounter itself — lock acquisition, LiveNode mount, node.run, fail-closed teardown, artifact finalize — becomes a small, safe piece of wiring behind the same nonce+TTY gate proven by the order-chain smokes, replacing a multi-step README recipe an operator retypes under live-market time pressure.
Axis
live-execution
Basis
direct: verified verbatim — live.rs:131-148 “installs the scrubber, enforces the paper interlock, and reports the staged status rather than touching the gateway… The live session… is documented as an operator recipe”; the teardown trait (live.rs:56-96) already encodes “engage the kill switch AFTER the closing cancels — always” and is unit-tested; the wiring proof exists (live_wiring.rs:61-85 mounts the ORB strategy in a built LiveNode).
Rationale
Every other live-execution safety primitive — kill switch, 300s dedup, dual-source fill ledger, six-state reconciliation, flat-start gate — is built and tested. They are stranded capital behind one missing wire. This is the single critical-path production blocker: no strategy or SDK polish matters until a session is a runnable command rather than a recipe. Framing “attended” as a software property (what exactly does the human add that a dead-man timer doesn’t?) converts the scariest unknown into an incremental extension of tested code.
Downsides
End-to-end verification needs live credentials and a KRX window — it cannot be fully proven by the offline gate, so the first wired sessions remain attended by design. Watchdog thresholds (heartbeat period, max-loss) need pre-registered values to avoid ad-hoc tuning mid-session.
Confidence
90% — the gap and every building block were verified in the repo; the risk is calibration, not existence.
Complexity
Medium

A statistical trust layer for the verdict machinery

Description
Four additions to the KEEP/REVERT gate, all bolted onto the existing pre-register/twin-verify harness: (a) a frozen out-of-sample fold — a KEEP must survive on held-out sessions, or report Walk-Forward Efficiency (OOS/IS RoR) against a ≥0.70 bar; (b) bootstrap confidence intervals — resample the closed trades and require the ΔRoR distribution (not the point estimate) to clear the gate; (c) a sample-reuse ledger — clinical-trial-style “alpha spending” that debits a pre-registered look budget each time a sample gates a verdict, retiring the sample when spent; (d) a parameter-plateau lattice — perturb the kept constants ±10–20% across ~50 vectors and require the head to sit on a plateau, not a spike.
Axis
orb-strategy
Basis
direct: verified in TURN-LOG.md — every CLASS B verdict v25→v30 was gated on the same 167 closed trades; the equity-compounding REVERT was decided on ΔRoR = −0.0008 with no dispersion estimate anywhere in the protocol; v30 carries six-significant-figure frozen constants (ratio_atr_ref 0.073158, w_lo/w_hi) whose neighborhood has never been tested. external: >90% of strong in-sample backtests fail out-of-sample; WFE ≥ 0.70 (walk-forward literature); Lan-DeMets alpha-spending functions; Pardo plateau analysis.
Rationale
The biggest strategy risk is not a bug — it is that v30’s edge may be a sample-mined artifact of six sequential looks at one dataset. The existing governance rigorously prevents within-turn p-hacking but is structurally blind to across-turn p-hacking. Several past verdicts (both KEEPs and REVERTs) were plausibly coin flips at n=167. This layer also converts “grow the sample via the #118 universe run” from a backlog item into a measured governance obligation.
Downsides
An OOS fold shrinks the already-small training sample; some past verdicts may un-decide (uncomfortable but honest). Bootstrap on a ratio-of-sums needs care with heavy-tailed trades. The plateau lattice is compute-heavy (though offline and gateway-free).

KRX session-truth module: calendar + opening-range integrity in one seam

Description
One shared KrxCalendar answering “is today a session?” plus a per-symbol session-integrity guard answering “is this opening range trustworthy right now?”. The calendar layers a pinned KRX holiday file with a cross-sectional absence classifier (if every symbol has zero bars on a weekday, it is a market closure; if only some, a coverage gap) that both backfills history and flags drift between the file and observed reality. The integrity guard checks first-bar timestamp vs expected open, intra-OR bar-count sanity, and mid-session gap detection (Volatility Interruptions), invalidating a symbol’s opening range with the established skip-not-reject pattern.
Axis
data-pipeline
Basis
direct: verified — last_weekday_on_or_before (research.rs:130) skips only Sat/Sun with no holiday table; KRX_REGULAR_OPEN: 09:00 is a hardcoded constant (rules.rs:31); the watermark advances decoupled from bar presence, a documented source of false GO signals. external: KRX Volatility Interruption mechanics and irregular one-off open delays (e.g., a 10:00 delayed open) that no static holiday file contains.
Rationale
The same missing-calendar bug appears independently in the lab audit path and the live ingest watermark (TODO #120), and the strategy’s entire signal is the opening range — under a delayed open, the OR computes over auction silence and produces plausible-looking garbage breakout levels on exactly the volatile days when losses are largest. Neither backtests nor paper smokes will ever surface that; it is a live-only landmine. Fixing calendar and range-integrity as one seam removes a whole class of false GO/NO-GO and bad-trade risk before any live rung.
Downsides
The cross-sectional classifier needs a wide-enough catalog to be decisive (thin universes weaken “all symbols silent”). VI detection from bar gaps is heuristic and needs tuning against false positives on illiquid symbols.

Durable order idempotency — persist the dedup reservation

Description
The order deduplicator is a pure in-memory DashMap with a 300-second window. Kill the process 50ms after an order POST and restart it: the cache is empty, the strategy re-emits, and the only remaining defense against a double fill is the asynchronous t0425-paced reconciler. Fix with the payments-industry pattern: write the reservation (an explicit client idempotency key + timestamp) to state/ before dispatch, load surviving reservations on startup, and refuse-or-reconcile-first on any key younger than the TTL. Making the key explicit (caller-supplied, not content-derived) also gives every future consumer — canary subsets, a second strategy, operator retries — safe-by-construction retry semantics.
Axis
live-execution
Basis
direct: verified by repo read — crates/ls-core/src/order_dedup.rs:58-72: cache: DashMap<String, CacheEntry>, no persistence, TTL-based opportunistic eviction only. external: payments/webhook idempotency keys — durable precisely because a client crash is the canonical duplicate generator.
Rationale
Every other order-safety layer here (kill switch, reservation ordering, six-state reconciliation) is fail-closed; this is the single fail-open gap, and it manifests only in production restart scenarios that paper smokes structurally never exercise. It is also a hard prerequisite for the watchdog/unattended designs in ideas 1–2, where restart-after-crash is the normal recovery path. Smallest survivor, disproportionate payoff.
Downsides
Adds a synchronous disk write to the order hot path (negligible at this strategy’s order rate); startup reconciliation logic needs care around clock skew and half-written reservations.

Tilt, don’t filter — revive the falsified levers through the proven weight slot

Description
Re-open the FALSIFIED lever axes not as threshold filters but as bounded multiplicative tilts in the anti-collapse budget-numerator slot that ratio-ATR just validated — the w = clamp((ref/x)^alpha, w_lo, w_hi) template with its Phase-A collinearity gate, frozen clamps, and bind-signature telemetry. The sharpest candidate is RVOL: its falsification as a floor found a real inverted signal (winners have lower opening RVOL) that a filter cannot exploit but a downweight-high-RVOL tilt can. Per repo convention, the two latent orb.rs bugs (the Some(0.0) prior-ATR stop collapse and the close-confirm same-bar stop ordering) ride this code turn’s re-baseline.
Axis
orb-strategy
Basis
direct: turn history — every threshold-filter lever (RVOL floor, entry cutoff, breakout-strength band, OR-width reject) was FALSIFIED or reverted, while both KEPT levers are continuous, clamped, cross-sectional reweights; the RVOL turn’s own finding: “INVERTED signal (winners have LOWER opening RVOL).” external: Harrell’s dichotomization critique — thresholding a continuous predictor destroys information and can invert its apparent sign.
Rationale
The falsified turns are booked as dead axes, but the pattern says the lever class was wrong, not the signal. Each revival is a cheap governed turn on a pre-warmed signal using machinery that just passed every gate — the highest expected-return-per-effort direction left in the queue. Idea 3’s trust layer should gate these verdicts, which is why it ranks above.
Downsides
Medium confidence by nature — the inverted RVOL signal may not survive a collinearity pre-gate against the kept ratio-ATR tilt, and per idea 3, verdicts on the current n=167 sample carry wide error bars. A Phase-A STOP (predicted-inert, no build) is a legitimate outcome.

Measure the folklore — per-lane rate-limit calibration + adaptive backoff

Description
The four per-category GCRA limiter rates (MarketData 5/s, Orders 3/s, Account 1/s, Auth 1/s) are configured constants inherited from paper experience — no measurement code touches them, unlike the cumulative IGW00201 budget which budget-probe already characterizes. Build a one-shot, credential-safe calibration probe per lane (ramp each category against a cheap read TR to first throttle; slow soak for the cumulative window), persist results to a per-lane limits file the RateLimiterManager loads, and upgrade the existing static measured backoff in budget.rs into an adaptive one that adjusts from observed IGW00201 responses rather than a committed constant.
Axis
sdk-hardening
Basis
direct: verifier-confirmed — the GCRA constants have no calibration code and are a separate layer from the budget-probe-measured cumulative budget; CONCEPTS.md: the budget’s “size, window, and exact bucket scope are not published anywhere and must be measured empirically.” external: KIS and Kiwoom publish hard ceilings that differ between paper and live accounts — LS’s paper-derived numbers may not predict live.
Rationale
Going live on paper-calibrated limits risks either throttle storms mid-session (live limits lower) or leaving multiples of ingest throughput on the table (live limits higher). Both directly hit the live path. A half-day probe converts folklore into per-lane measured facts; the adaptive backoff moves hard-won pacing knowledge out of TODO notes (“t8430 LAST, self-pace”) into the dispatch layer every caller inherits. Note: the adversarial verifier corrected the fleet’s original framing here — budget.rs already has a real Defer/Proceed scheduler; the genuine gap is calibration of the GCRA layer and adaptivity of the backoff, which is how this idea is scoped.
Downsides
The probe itself spends gateway budget and needs an attended window; live-lane calibration can only happen once live credentials exist, so this partially queues behind idea 2. Adaptive backoff needs guardrails to avoid oscillation.

70%
