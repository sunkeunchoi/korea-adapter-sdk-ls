0. 결론 3개 — TL;DR

결론 1 · 모델 분리는 맞다

분석은 Opus 4.8(=이 문서)로 끝내고, 계획+실행은 Fable로. 분석은 짧고·고레버리지·오류가 하류로 전파되는 단계라 무거운 추론 모델에 투자하는 게 이득이고, 산출물이 문서라 모델 교체 시 컨텍스트 손실이 없다(문서=공유 컨텍스트). 덤으로 "분석 모델 ≠ 계획 모델"은 이 레포가 이미 애용하는 교차-모델 검증을 공짜로 얻는다. (§6)

결론 2 · Clean/Hexagonal 통짜 도입 = 범주 오류

그 패러다임들은 의존성 방향과 비즈니스 로직 격리를 푸는 도구다. 그런데 이 코드의 "길이"는 그 문제가 아니다. 이건 라이브러리(SDK)이고 로직은 이미 ls-core에 얇게 격리돼 있다. 길이의 정체는 320개 TR × 기계적 DTO 보일러플레이트다. Clean/Hexagonal을 올려도 이 물량은 한 줄도 안 줄고 ceremony만 는다. (§2, §4)

결론 3 · 진짜 레버 = 메타데이터 기반 codegen

이 프로젝트는 이미 320개 TR의 wire-shape를 구조화된 형태로 보유한다(normalized/trs/*.json + metadata/trs/*.yaml). 이미 그걸로 문서를 생성한다(ls-docgen). DTO 스켈레톤 생성은 그 자연스러운 확장이자 이 프로젝트에만 열린 고유 수단이다. 우선순위: codegen > 선언적 매크로 > 모듈 분해 계속 > vertical-slice 형식화. (§5)

2. "길이" 문제의 진짜 정체

ls-sdk가 61k LOC인 이유는 아키텍처 얽힘이 아니라 형식적 DTO의 물량이다. 증거물로 t8425(전체테마, 가장 단순한 read)를 보자:

#[derive(Serialize, Debug, Clone)]
pub struct T8425InBlock { pub dummy: String }        // 요청 필드 목록

#[derive(Serialize, Debug, Clone)]
pub struct T8425Request {                            // "t8425InBlock" 키로 감싸는 봉투
    #[serde(rename = "t8425InBlock")] pub inblock: T8425InBlock,
}
impl T8425Request { pub fn new() -> Self { /* ... */ } }
impl Default for T8425Request { /* ... */ }

#[derive(Serialize, Deserialize, Debug, Clone, Default)]
#[serde(default)]
pub struct T8425OutBlock {                            // 응답 한 행
    #[serde(deserialize_with = "ls_core::string_or_number")] pub tmname: String,
    #[serde(deserialize_with = "ls_core::string_or_number")] pub tmcode: String,
}

#[derive(Serialize, Deserialize, Debug, Clone, Default)]
pub struct T8425Response {                            // 봉투 + rsp_cd/rsp_msg + 배열-혹은-단일
    #[serde(default)] pub rsp_cd: String,
    #[serde(default)] pub rsp_msg: String,
    #[serde(rename = "t8425OutBlock", default, deserialize_with = "ls_core::de_vec_or_single")]
    pub outblock: Vec<T8425OutBlock>,
}

이 ~90줄(주석 포함) 중 구조적으로 결정되는 부분은 이미 프로젝트가 구조화해 보유한다:

// normalized/trs/t8425.json — 필드-레벨 wire shape (이미 존재)
{ "direction":"request", "block_name":"...", "field_name":"tr_cd",
  "korean_name":"거래 CD", "type":"String", "length":10, "required":true }
  • InBlock/OutBlock의 필드명·타입·length·required → baseline JSON에 있음
  • Request 봉투, new(), Default, rsp_cd/rsp_msg + de_vec_or_single → 모든 TR 동일 패턴
  • 배열-vs-단일, self-pagination, rate bucket, protocol → metadata/trs/*.yaml facets에 있음

320벌 × ~90줄의 대부분은 프로젝트가 이미 들고 있는 구조화 데이터의 손번역본이다. 그러므로 길이의 해법은 "구조를 바꾸는 것"이 아니라 "물량을 생성으로 대체하는 것"이다. 아키텍처 패러다임은 물량 문제를 못 푼다.

3. 현재 아키텍처 평가 — 이미 꽤 좋다

                    ┌─────────────────────────────────────────┐
   호출자 (앱)  ──▶ │  ls-sdk  (Driving Adapter / 공개 API)     │
                    │  LsSdk facade → 도메인별 핸들:            │
                    │   standalone · market_session · paginated │
                    │   account · orders · fo_orders · realtime │
                    └───────────────┬─────────────────────────┘
                                    │  Arc<Inner> (공유 런타임)
                    ┌───────────────▼─────────────────────────┐
                    │  ls-core  (Application Core / 런타임)     │
                    │   Inner::post / post_paginated / post_order│
                    │   endpoint_policy/{market_data, order,     │
                    │     realtime_md, realtime_order, auth, ...} │
                    │   rate_limiter · auth · preflight · error  │
                    └───────────────┬─────────────────────────┘
                                    │  HTTP / WebSocket → LS 게이트웨이

  ┌──────── 메타데이터/툴링 평면 (Source of Truth) ────────┐
  │ metadata/*.yaml + normalized/*.json → ls-docgen → docs/ │
  │ ls-metadata (validator) · ls-trackers (drift/freshness) │
  └─────────────────────────────────────────────────────────┘
  • 관심사 분리는 이미 크레이트 경계로. transport(ls-core) ↔ 공개 API(ls-sdk) ↔ 메타데이터/툴링. 서로 다른 축의 변경이 서로를 오염시키지 않는다.
  • Hexagonal 골격이 이미 있다. ls-core=도메인-무관 코어(hexagon), endpoint_policy/*=도메인별 정책 포트, facade 핸들=driving adapter, 게이트웨이=driven side.
  • Vertical Slice도 이미 사실상 적용됨. market_session / paginated / account / orders / realtime는 레이어가 아니라 의존성-클래스(feature) 슬라이스. lib.rs 주석: "Dependency classes are modules ... tests routed by metadata facet, not by module boundary." — vertical slice 그 자체.

사용자가 "도입할까" 고민 중인 셋 중 둘(Hexagonal 코어/어댑터 분리, Vertical Slice)은 이미 코드에 내재해 있다. 남은 건 "도입"이 아니라 "형식화/일관화"다.

4. 패러다임 적합성 판정

패러다임무엇을 푸는가이 프로젝트에 필요한가판정
Clean Architecture 엔티티/유스케이스를 동심원으로, 의존성이 안쪽으로만 이 SDK엔 유스케이스/엔티티 계층이 없다. 로직은 dispatch 정책뿐이고 이미 ls-core에 격리됨. 계층을 올리면 320 TR마다 빈 껍데기만 늘어남 ❌ 도입 금지
물량 미해결 + ceremony 폭증
Hexagonal 코어 로직을 I/O(어댑터)와 분리 골격이 이미 있음(ls-core=코어, facade=어댑터). "정식 hexagonal"로 리네이밍/추상화할 실익 적음 🟡 이미 있음
용어/경계 문서화만
Vertical Slice 레이어 아닌 기능(슬라이스) 단위 조직 이미 dependency-class 모듈 = 슬라이스, 테스트도 facet 기반 🟢 이미 채택
"완성/형식화"만
메타데이터 Codegen 구조화된 명세로부터 반복 코드 생성 320 TR × 기계적 DTO = 정확히 이 문제. 명세(baseline+yaml)와 생성 인프라(docgen) 이미 보유 ✅ 이게 정답
유일하게 길이를 실제 공격

한 문장: 후보로 든 셋은 앱 아키텍처 도구인데 이 프로젝트의 통증은 라이브러리의 DTO 물량이다. 셋 중 유효한 부분은 이미 코드에 있고, 진짜 해법(codegen)은 후보에 없었다.

5. 권장 리팩터링 레버 (우선순위순)

레버 1 — 메타데이터 기반 DTO codegen ⭐ 최고 레버리지

  • 무엇: normalized/trs/*.json + metadata/trs/*.yaml로부터 InBlock/Request/new/Default/OutBlock/Response 스켈레톤 생성. ls-docgen 확장 또는 형제 ls-sdk-gen.
  • 이 프로젝트에서만 가능한 이유: source of truth가 이미 구조화돼 있고, make docs/docs-check로 "생성물==커밋" 검증 파이프라인도 이미 있음. 같은 파이프라인에 태우면 됨.
  • 효과: 신규 TR 손코딩 ≈ 0 · wire drift 자동 전파 · 기계적 부분 일회 대폭 축소.
⚠️ 반드시 하이브리드 (프로젝트 기존 교훈 반영)
  • Response/OutBlock: baseline이 응답 shape의 권위 → 자신 있게 생성.
  • Request/InBlock: baseline은 request 블록을 과소보고할 수 있고, live-certified 손작성 구조체가 이긴다(docs/solutions/conventions/normalized-baseline-can-underreport-request-block.md). 생성물은 시작 스켈레톤, override 가능해야 함. 눈 감고 전량 생성 금지.
  • doc 주석: 사람이 쓴 산문은 생성 불가 → 사실 기반 stub만.
  • 숫자 request 필드 = string_as_number(JSON 숫자, 아니면 IGW40011). F/O 가격 소수 = string_as_decimal.

정직한 기대치: "61k줄 삭제"가 아니라 성장 멈춤 + 기계적 부분 축소. doc-heavy 파일은 0으로 안 줄어든다. 비용/리스크 中.

레버 2 — 선언적 매크로 tr! 경량 대안/디딤돌

  • Request 봉투 + new + Default + Response 동일 패턴을 macro_rules!로. 선례: rank_screen.rs의 rank_row!/idx_summary!.
  • 각 TR의 ~40%(봉투/impl 반복) 흡수. baseline override 문제 안 건드림. codegen이 부담되면 여기부터, 나중에 승격. 비용/리스크 低.

레버 3 — 모듈 분해 계속 검증된 패턴

  • 남은 대형 파일(chart.rs 2,304 등)을 pub use submod::*; 순수 relocation으로 계속 쪼갬. count·crosscheck 무변경.
  • 주의: relocation은 실패가 조용함 → 검증은 컴파일러가 아니라 --list 테스트명 스냅샷 diff(PR #78 교훈). 비용/리스크 低.

레버 4 — Vertical slice 형식화 구조 아님, 규칙

  • 신규 TR이 항상 owner_class(facet) → 올바른 슬라이스로 떨어지도록 track-tr/implement-tr 레시피에 명문화. 이미 사실상 지켜지니 "규칙 고정"만.
하지 말 것

Clean/Hexagonal 대공사(빅뱅 재설계) — 물량 미해결 + gate 결합(§7) 대규모 파손 위험. 메타데이터 source-of-truth나 test crosscheck 리스트와 싸우는 어떤 변경도 금지.

6. 모델 선택 전략 — 왜 "Opus 분석 / Fable 계획·실행"인가

결정 규칙: 짧고 고레버리지인 사고는 가장 무거운 추론 모델에, 길고 기계적인 실행은 가장 효율적인 최신 모델에. 그리고 각 단계를 상대 모델로 교차 검증.

단계성격권장 모델이유
분석 (지금)짧음·고레버리지·오류가 전 하류로 전파Opus 4.8방향을 정하는 단계. 여기서 틀리면 계획·실행이 통째로 틀림. 산출물이 문서라 모델 교체 시 컨텍스트 손실 0
계획다수 모듈에 걸친 설계Fable물량 작업. + 분석(Opus)과 다른 모델이라 교차-모델 검증이 공짜로 붙음
실행100개 파일 편집·생성 반복Fable처리량이 곧 비용. 최신·효율 모델의 throughput이 복리로 이득
리뷰계획/코드 검증상대 모델이 레포는 이미 "cross-model Codex 리뷰"를 상시 사용(메모리 다수). 관성과 일치

"전부 Fable로" 대안은 언제 맞나: 단일 모델 일관성·낮은 비용을 교차검증보다 더 칠 때, 또는 실사용에서 Fable의 아키텍처 추론이 Opus와 대등하다고 느낄 때. 이 경우 손실은 "교차-모델 다양성"뿐이고, 산출물이 문서라 컨텍스트 연속성은 어차피 문제되지 않는다.

추천

분석은 이미 Opus로 확정(=이 문서). 계획·실행은 Fable. 그리고 Fable의 계획을 Opus로 1회 리뷰(§7을 체크리스트로). 짧은 고가치 사고엔 비싼 모델, 긴 기계 작업엔 효율 모델 — 이 프로젝트의 phase 구조와 정확히 맞는다.

7. 리스크 & 제약 (계획 모델에 반드시 전달)

이 레포는 gate 머신러리가 현재 구조에 강하게 결합돼 있다. 존중하지 않으면 green gate가 대량 파손된다.

  1. Count 리터럴 결합: ls-docgen/src/lib.rs의 reference.len()(현 280)·banner_trs, ls-trackers/src/cli.rs count 리터럴은 make docs로 안 잡히고 cargo test로만 잡힘.
  2. Crosscheck 이원화: 신규 REST {TR}_POLICY는 두 리스트 모두에. WS policy(owner_class: realtime)는 crosscheck에만, slice_rest_policies_are_non_order_rest엔 절대 금지.
  3. 순수 relocation 트릭: pub use submod::*;로 공개 경로 불변. use super::*가 부모의 private import까지 glob으로 끌어와 순수 이동이 컴파일됨 — codegen 출력도 이 관례 준수.
  4. Baseline 과소보고: request 블록에서 baseline < 실제 가능. certified 손작성 구조체 우선(§5 레버1).
  5. 숫자 request 필드: string_as_number 안 쓰면 IGW40011. F/O 가격 소수 = string_as_decimal.
  6. ls-trackers 포맷 금지: main이 의도적으로 unformatted. 전체 cargo fmt = 거대한 헛디프.
  7. 분해 실패는 조용함: 검증은 컴파일이 아니라 --list 스냅샷 diff. 한국어 문자열 테스트는 locale 트랩(LC_ALL=C 고정).
  8. MEMORY.md 초과: 현재 29.3KB > 24.4KB 한도. 이 작업 기록을 memory에 넣으려면 index 한 줄로만.

8. 추천 실행 순서 (phased, Fable 담당)

  • Phase 0 (설계, Opus 리뷰 대상): codegen 스코프 확정 — Response 전량 / Request 스켈레톤+override 경계 / doc stub 정책. gate 결합(§7) 대응.
  • Phase 1 (PoC): 대표 TR 3~5개(단순 read t8425 · paginated · 배열형 · request 있는 것 · order 계열)에 codegen 적용, "생성물==커밋" 검증(docs-check 방식) 붙이기. gate green 증명.
  • Phase 2 (확대): read 계열로 확대. 파일별 순수 relocation 병행.
  • Phase 3 (경계 케이스): certified override 필요한 request/order 계열 신중히. baseline 과소보고 대조.
  • Phase 4 (형식화): 신규 TR이 codegen+올바른 슬라이스로 떨어지도록 레시피 갱신.

각 Phase = 독립 PR + cargo test/docs-check/lane-check green + ce-code-review(레포 관례).

9. 계획 프롬프트 (Fable 세션용)

전문은 별도 파일: docs/brainstorms/2026-07-02-refactoring-planning-prompt.md (변형 A/B 포함). 아래는 본체.

[역할] 너는 korea-adapter-sdk-ls (LS증권 Open API Rust SDK) 리팩터링 계획을
수립하는 시니어 Rust 아키텍트다. 실행이 아니라 "구현 가능한 계획"을 만든다.

[확정된 방향 — 재논의 금지]
- 이건 라이브러리(SDK)다. Clean/Hexagonal 통짜 도입은 하지 않는다(범주 오류).
  Hexagonal 코어/어댑터 분리와 Vertical Slice는 이미 코드에 내재 → "형식화"만.
- "길이" 문제의 정체는 320개 TR × 기계적 DTO 보일러플레이트다(아키텍처 얽힘 아님).
- 채택 레버 우선순위: (1) 메타데이터 기반 DTO codegen  (2) 선언적 tr! 매크로
  (3) 모듈 분해 계속(pub use submod::*)  (4) vertical-slice 규칙 형식화.
  근거: docs/brainstorms/2026-07-02-refactoring-strategy-and-architecture-analysis.md

[목표] 레버 (1)을 중심으로 단계별(PoC→확대→경계→형식화) 구현 계획을 작성.
각 단계는 독립 PR 단위, gate green 유지, 롤백 가능해야 한다.

[반드시 반영할 제약 (틀리면 gate 파손)]
1. codegen 소스: crates/ls-trackers/baselines/api-drift/normalized/trs/<tr>.json
   + metadata/trs/<tr>.yaml. ls-docgen이 이미 이 소스로 문서 생성 중 →
   같은 파이프라인/검증(make docs, docs-check)에 태울 것.
2. 하이브리드 생성:
   - Response/OutBlock: baseline이 권위 → 전량 생성.
   - Request/InBlock: baseline 과소보고 가능. live-certified 손작성 구조체 우선
     (docs/solutions/.../normalized-baseline-can-underreport-request-block.md).
     생성물은 시작 스켈레톤. 눈 감고 전량 생성 금지.
   - doc 주석 산문은 생성 불가 → 사실 기반 stub만.
   - 숫자 request 필드 = string_as_number(아니면 IGW40011). F/O 가격 = string_as_decimal.
3. Count/crosscheck 결합: reference.len()·banner_trs·cli.rs count 리터럴은
   make docs로 안 잡히고 cargo test로만. 신규 REST {TR}_POLICY는 두 crosscheck
   리스트 모두에, WS policy는 crosscheck에만.
4. 순수 relocation은 pub use submod::*; + use super::*; 관례 유지. 분해 검증은
   컴파일이 아니라 cargo test --list 스냅샷 diff. 한국어 문자열은 LC_ALL=C.
5. ls-trackers 크레이트는 cargo fmt 금지(main이 의도적으로 unformatted).

[산출물] 단계별 계획(Phase 0~4). 각 Phase: 목표/변경 파일/검증/롤백/리스크.
